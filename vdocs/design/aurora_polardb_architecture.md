## 1. Amazon Aurora

### 1.1 架构设计

Amazon Aurora 是 AWS 推出的云原生关系型数据库服务，发表于 **SIGMOD 2017**，是云原生数据库的开创性产品。Aurora 的核心设计理念是**存储与计算分离**，通过将存储层和计算层解耦，实现了高性能、高可用性和高扩展性。

#### 主要架构特点：

1. **计算与存储分离**
   - **计算层**：由数据库实例组成，负责处理 SQL 查询、事务管理、锁管理等
   - **存储层**：由分布式存储系统组成，负责数据持久化和副本管理

2. **多副本高可用**
   - 数据在存储层跨 **3 个可用区（Availability Zone）** 存储
   - 每个数据块维护 **6 个副本**（每个 AZ 2 个副本）
   - 采用 **4/6 Quorum 协议**：
     - 写入操作：至少 4 个副本确认即可返回成功
     - 读取操作：至少 3 个副本确认即可返回成功
   - 可容忍 1 个 AZ + 1 个副本同时失败，仍保持可用

3. **日志即数据库（Log is Database）**
   - 只传输 Redo Log，不传输数据页
   - 存储层负责应用 Redo Log 生成数据页
   - 大幅减少网络 I/O（约减少 35 倍）

4. **扩展性**
   - 存储：自动扩展，最大支持 **128 TB**
   - 计算：支持最多 **15 个只读副本**
   - 读副本延迟：通常小于 **100 毫秒**

### 1.2 核心技术特性

#### 1. **Redo Log 处理流程**

```
传统数据库：
Write Redo Log → Write Data Page → Replicate to Standby → Persist to Disk

Aurora：
Write Redo Log → Async Write to 6 Storage Nodes (Wait for 4 ACKs)
```

#### 2. **性能优化**

- **吞吐量**：相比标准 MySQL 提升 **5 倍**
- **延迟**：写入延迟降低至几毫秒
- **网络流量**：减少约 **35 倍**（只传输 Redo Log）

#### 3. **故障恢复**

- **自动故障检测**：持续监控存储节点健康状态
- **快速故障转移**：通常在 **30 秒内**完成主节点切换
- **无损故障转移**：通过 Quorum 机制保证数据不丢失

### 1.3 主从同步机制

Aurora 的主从同步基于**共享存储架构**，与传统的主从复制有本质区别：

#### 传统主从复制 vs Aurora 复制

| 特性 | 传统主从复制 | Aurora 复制 |
|-----|------------|------------|
| 数据传输 | 完整数据页 + Binlog | 仅 Redo Log |
| 存储方式 | 各节点独立存储 | 共享存储层 |
| 复制延迟 | 秒级或分钟级 | 毫秒级（< 100ms）|
| 故障转移时间 | 分钟级 | 秒级（< 30s）|
| 网络开销 | 高 | 低（减少 35 倍）|

#### Aurora 复制流程

1. **写入流程**
   - 主实例执行事务，生成 Redo Log
   - Redo Log 并行发送到 6 个存储节点
   - 等待至少 4 个节点确认（4/6 Quorum）
   - 向客户端返回事务提交成功

2. **读取流程**
   - 读副本共享相同的存储层
   - 读副本从存储层读取 Redo Log
   - 读副本在内存中应用 Redo Log，保持数据一致性
   - 读副本可直接服务查询请求

3. **一致性保证**
   - 采用 **LSN（Log Sequence Number）** 追踪日志位置
   - 读副本追踪主实例的 LSN，确保读取一致性
   - 通过 **VCL（Volume Complete LSN）** 管理已持久化的日志位置

## 2. 阿里云 PolarDB

### 2.1 架构设计

阿里云 PolarDB 是阿里云推出的云原生关系型数据库，核心论文发表于 **VLDB 2021** 和 **SIGMOD 2023**（PolarDB-IMCI）。PolarDB 同样采用**存储与计算分离**的架构，并在此基础上进行了多项创新。

#### 主要架构特点：

1. **计算与存储分离**
   - **计算层**：包含一个读写节点和多个只读节点（最多 16 个）
   - **存储层**：基于分布式共享存储 PolarFS，采用 RDMA 网络

2. **存储架构：PolarFS**
   - 基于用户态文件系统
   - 采用 **ParallelRaft** 协议（改进的 Raft）
   - 支持 **RDMA** 网络，降低延迟
   - 三副本存储，支持跨可用区

3. **低延迟复制**
   - 采用 **物理复制**（基于 WAL 日志）
   - 支持 **并行回放**（Parallel Replay）
   - 只读节点延迟可控制在 **毫秒级**

4. **HTAP 支持**
   - **PolarDB-IMCI**：内存列式索引
   - 支持 OLTP 和 OLAP 混合负载
   - 列存和行存混合存储

### 2.2 核心技术特性

#### 1. **PolarFS 分布式存储**

```
特性：
• 用户态文件系统，减少内核态切换
• RDMA 网络，降低延迟至 10 微秒级
• ParallelRaft：并行化的 Raft 协议，提升吞吐量
• 支持快照和克隆功能
```

#### 2. **并行日志回放**

PolarDB 采用多线程并行回放 WAL 日志，大幅提升只读节点的追赶速度：

- **Page 级并行**：不同数据页的日志可以并行回放
- **依赖分析**：自动分析日志间的依赖关系
- **动态调度**：根据系统负载动态调整并行度

#### 3. **共享缓冲池**

- 读写节点和只读节点共享存储层
- 只读节点维护本地缓冲池
- 通过 **Buffer Invalidation** 机制保持缓存一致性

#### 4. **PolarDB-IMCI（内存列式索引）**

- 在行存基础上构建列式索引
- 实时同步 OLTP 数据到列存
- 支持复杂分析查询加速

### 2.3 主从同步机制

PolarDB 的主从同步基于**物理日志复制**，结合了共享存储和异步复制的优势：

#### PolarDB 复制特性

| 特性 | PolarDB | 传统主从 |
|-----|---------|---------|
| 复制类型 | 物理复制（WAL） | 逻辑复制（Binlog）|
| 延迟 | 毫秒级 | 秒级 |
| 并行度 | 高（并行回放）| 有限 |
| 存储 | 共享存储 | 独立存储 |
| 一致性 | 最终一致性 | 最终一致性 |

#### PolarDB 复制流程

1. **写入流程**
   - 读写节点生成 WAL 日志
   - WAL 日志写入共享存储（PolarFS）
   - 通过 ParallelRaft 协议同步到 3 个副本
   - 至少 2 个副本确认后返回成功

2. **只读节点回放流程**
   - 只读节点订阅主节点的 WAL 日志流
   - 通过 RDMA 网络获取 WAL 日志
   - 并行回放 WAL 日志到本地缓冲池
   - 更新本地 LSN，追踪回放进度

3. **一致性保证**
   - 主节点维护 **Flush LSN**：已刷盘的日志位置
   - 只读节点维护 **Replay LSN**：已回放的日志位置
   - 主节点控制刷脏速度，不超过最慢只读节点的回放位置
   - 通过 **Consistent Read View** 保证读一致性

### 3.3 优缺点对比

#### Aurora 优势：
- ✅ **高可用性**：6 副本 + 4/6 Quorum，可容忍更多故障
- ✅ **成熟稳定**：AWS 运营多年，生态完善
- ✅ **日志即数据库**：创新的架构设计，网络流量减少 35 倍
- ✅ **全球部署**：AWS 全球多区域支持

#### Aurora 劣势：
- ❌ **网络延迟**：基于 TCP/IP，延迟相对较高
- ❌ **HTAP 支持弱**：对混合负载支持有限
- ❌ **厂商锁定**：只能在 AWS 上使用

#### PolarDB 优势：
- ✅ **低延迟**：RDMA 网络，延迟降至 10 微秒级
- ✅ **并行回放**：多线程并行应用 WAL，复制更快
- ✅ **HTAP 能力强**：PolarDB-IMCI 列存，支持混合负载
- ✅ **快速克隆**：写时复制技术，秒级克隆数据库
- ✅ **Oracle 兼容**：支持 Oracle 语法，便于迁移

#### PolarDB 劣势：
- ❌ **副本数较少**：3 副本，容错能力弱于 Aurora
- ❌ **生态相对弱**：国际化程度不如 AWS
- ❌ **依赖 RDMA**：需要特定网络硬件支持

### 3.4 适用场景

#### Aurora 适合：
- 需要极高可用性的关键业务（金融、支付）
- AWS 云上的应用
- 需要全球部署的应用
- 读多写少的 OLTP 场景

#### PolarDB 适合：
- 需要低延迟的高性能场景
- HTAP 混合负载（同时支持 OLTP 和 OLAP）
- 需要快速克隆和开发测试环境
- 从 Oracle 迁移的场景
- 阿里云生态的应用

## 总结

**Aurora** 和 **PolarDB** 都是优秀的云原生数据库，代表了云数据库的发展方向。两者都采用了**存储与计算分离**的架构，但在具体实现上有各自的创新：

- **Aurora** 通过 **6 副本 + 4/6 Quorum** 实现了极高的可用性，通过 **日志即数据库** 理念大幅减少网络流量。
  
- **PolarDB** 通过 **RDMA 网络 + 并行回放** 实现了更低的延迟，通过 **PolarDB-IMCI** 提供了强大的 HTAP 能力。

选择哪个数据库，取决于具体的业务需求、云平台选择和技术栈。两者都是云数据库领域的标杆产品，值得深入学习和研究。
