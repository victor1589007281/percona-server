# Writeset 依赖跟踪与并行复制冲突检测深度解析

## 备选标题

1. **MySQL Writeset揭秘：让并行复制性能翻倍的黑科技**
2. **深入理解事务依赖跟踪：从COMMIT_ORDER到WRITESET的进化**
3. **数据库专家必读：Writeset冲突检测与commit_id分配的底层原理**

## 一、开篇引子

> 想象你在图书馆整理书籍：传统方式是按照借阅顺序依次归还；而更聪明的方式是检查每本书的书架位置——只要不在同一个架子上，就可以同时归还。MySQL的Writeset就是这个"书架检查"机制，通过分析事务修改了哪些行，来判断哪些事务可以并行回放。

在并行复制中，如何确定两个事务是否可以并行执行是核心问题。MySQL提供了三种依赖跟踪策略：

1. **COMMIT_ORDER**：基于主库提交顺序（Group Commit窗口）
2. **WRITESET**：基于事务修改的行集合
3. **WRITESET_SESSION**：WRITESET + 同会话事务顺序保证

本文基于 **Percona Server 8.4.3-3** 源码，深入剖析Writeset的工作原理，包括冲突检测算法、commit_id分配机制，以及基于锁的冲突检测对比。

### 2.1 三种依赖跟踪策略对比

```
┌─────────────────────────────────────────────────────────────────────────────┐
│              binlog_transaction_dependency_tracking 三种策略对比             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  ┌────────────────────────────────────────────────────────────────────┐    │
│  │                      COMMIT_ORDER                                  │    │
│  │                                                                    │    │
│  │   依据: 主库Group Commit窗口                                       │    │
│  │   原理: 同一个Group Commit内的事务，last_committed相同             │    │
│  │                                                                    │    │
│  │   T1(lc=10)  T2(lc=10)  T3(lc=10)  │  T4(lc=11)  T5(lc=11)       │    │
│  │   ─────────────────────────────────┼──────────────────────────     │    │
│  │          Group 1                   │       Group 2                 │    │
│  │          可并行                     │       可并行                  │    │
│  │                                    │                               │    │
│  │   局限: 依赖主库并发度，单线程写入时无并行                          │    │
│  │                                                                    │    │
│  └────────────────────────────────────────────────────────────────────┘    │
│                                                                             │
│  ┌────────────────────────────────────────────────────────────────────┐    │
│  │                       WRITESET                                     │    │
│  │                                                                    │    │
│  │   依据: 事务修改的行集合(主键/唯一键hash)                           │    │
│  │   原理: 如果两个事务修改的行集合不相交，则可并行                      │    │
│  │                                                                    │    │
│  │   T1: UPDATE t SET x=1 WHERE id=1  →  hash(t,PRIMARY,1)           │    │
│  │   T2: UPDATE t SET x=2 WHERE id=2  →  hash(t,PRIMARY,2)           │    │
│  │   T3: UPDATE t SET x=3 WHERE id=1  →  hash(t,PRIMARY,1) 冲突!     │    │
│  │                                                                    │    │
│  │   T1与T2可并行(不同行)，T3必须在T1后执行(同行)                       │    │
│  │                                                                    │    │
│  │   优势: 即使主库串行，从库也能识别出可并行的事务                      │    │
│  │                                                                    │    │
│  └────────────────────────────────────────────────────────────────────┘    │
│                                                                             │
│  ┌────────────────────────────────────────────────────────────────────┐    │
│  │                    WRITESET_SESSION                                │    │
│  │                                                                    │    │
│  │   依据: WRITESET + 同一会话内事务顺序                               │    │
│  │   原理: 在WRITESET基础上，保证同一会话的事务顺序                     │    │
│  │                                                                    │    │
│  │   Session 1: T1 → T3 → T5  (必须按此顺序)                          │    │
│  │   Session 2: T2 → T4      (必须按此顺序)                           │    │
│  │   但 T1和T2 可能并行 (如果不冲突)                                   │    │
│  │                                                                    │    │
│  │   使用场景: 业务依赖会话内事务顺序的场景                             │    │
│  │                                                                    │    │
│  └────────────────────────────────────────────────────────────────────┘    │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

│  │                              ▼                                       │  │

### 3.1 Writeset Hash生成原理

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                     Writeset Hash 生成详细原理                               │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  【PKE (Primary Key Equivalent) 构建规则】                                   │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │                                                                      │  │
│  │   PKE字符串格式:                                                     │  │
│  │   ┌─────────────────────────────────────────────────────────────┐   │  │
│  │   │  INDEX_NAME + DB_NAME + TABLE_NAME + COLUMN_VALUES          │   │  │
│  │   └─────────────────────────────────────────────────────────────┘   │  │
│  │                                                                      │  │
│  │   示例表: CREATE TABLE test.t1 (                                    │  │
│  │              id INT PRIMARY KEY,                                    │  │
│  │              name VARCHAR(50) UNIQUE KEY,                           │  │
│  │              age INT                                                │  │
│  │           );                                                        │  │
│  │                                                                      │  │
│  │   INSERT INTO test.t1 VALUES (1, 'alice', 25);                     │  │
│  │                                                                      │  │
│  │   生成的PKE字符串:                                                   │  │
│  │   ┌─────────────────────────────────────────────────────────────┐   │  │
│  │   │  1. "PRIMARY" + "test" + "t1" + "1"                         │   │  │
│  │   │     → "PRIMARYtest2t121"                                    │   │  │
│  │   │                                                              │   │  │
│  │   │  2. "name" + "test" + "t1" + "alice"                        │   │  │
│  │   │     → "nametest2t12alice5"                                  │   │  │
│  │   │     (包含字符串长度以区分不同值)                              │   │  │
│  │   └─────────────────────────────────────────────────────────────┘   │  │
│  │                                                                      │  │
│  │   Hash计算:                                                          │  │
│  │   ┌─────────────────────────────────────────────────────────────┐   │  │
│  │   │  hash1 = MY_XXH64("PRIMARYtest2t121", len, 0)               │   │  │
│  │   │        = 16097759999475440183                                │   │  │
│  │   │                                                              │   │  │
│  │   │  hash2 = MY_XXH64("nametest2t12alice5", len, 0)             │   │  │
│  │   │        = 7001586410307804499                                 │   │  │
│  │   └─────────────────────────────────────────────────────────────┘   │  │
│  │                                                                      │  │
│  │   事务Writeset = {16097759999475440183, 7001586410307804499}        │  │
│  │                                                                      │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│  【为什么使用Hash而不是原始键值】                                            │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │                                                                      │  │
│  │  1. 空间效率: hash固定64位，原始键值可能很长                         │  │
│  │  2. 比较效率: 整数比较比字符串比较快                                  │  │
│  │  3. 隐私安全: 不暴露实际数据内容                                      │  │
│  │  4. 冲突概率: xxHash64冲突概率极低(2^-64)                            │  │
│  │                                                                      │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 基于锁的COMMIT_ORDER依赖检测原理

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                  COMMIT_ORDER 锁窗口依赖检测原理                              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  【核心思想】                                                                │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │                                                                      │  │
│  │  如果两个事务在主库上有锁持有时间窗口重叠，                            │  │
│  │  则它们在从库上也可以并行执行（不会有锁冲突）                          │  │
│  │                                                                      │  │
│  │  窗口定义:                                                            │  │
│  │  - 开始: 事务获取所有锁（prepare阶段）                                │  │
│  │  - 结束: 事务释放所有锁（commit阶段）                                 │  │
│  │                                                                      │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│  【Logical Clock 机制】                                                     │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │                                                                      │  │
│  │  两个关键时钟:                                                        │  │
│  │                                                                      │  │
│  │  ┌─────────────────────────────────────────────────────────────────┐│  │
│  │  │ m_transaction_counter:                                          ││  │
│  │  │   - 递增的事务计数器                                             ││  │
│  │  │   - 每个事务进入flush阶段时递增                                  ││  │
│  │  │   - 作为事务的sequence_number                                   ││  │
│  │  └─────────────────────────────────────────────────────────────────┘│  │
│  │                                                                      │  │
│  │  ┌─────────────────────────────────────────────────────────────────┐│  │
│  │  │ m_max_committed_transaction:                                    ││  │
│  │  │   - 已提交事务的最大sequence_number                             ││  │
│  │  │   - 事务提交后更新                                               ││  │
│  │  │   - 作为后续事务的last_committed基准                            ││  │
│  │  └─────────────────────────────────────────────────────────────────┘│  │
│  │                                                                      │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│  【时间线图解】                                                              │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │                                                                      │  │
│  │  时间 ──────────────────────────────────────────────────────────▶   │  │
│  │                                                                      │  │
│  │  max_committed: 99                100               101              │  │
│  │                  │                  │                 │               │  │
│  │                  │                  │                 │               │  │
│  │  T1(seq=100):   [=======执行=======]                                 │  │
│  │                  ↑prepare          ↑commit                           │  │
│  │                                     └─ update max_committed=100      │  │
│  │                                                                      │  │

// ============================================================================
// sql/rpl_trx_tracking.cc:212-294
// Writeset依赖计算核心代码
// ============================================================================
void Writeset_trx_dependency_tracker::get_dependency(
    THD *thd, int64 &sequence_number, int64 &commit_parent) {
  
  // 获取事务的writeset上下文
  Rpl_transaction_write_set_ctx *write_set_ctx =
      thd->get_transaction()->get_transaction_write_set_ctx();
  std::vector<uint64> *writeset = write_set_ctx->get_write_set();

  // 【关键】检查是否可以使用writeset进行依赖优化
  bool can_use_writesets = 
      // writeset不为空(空意味着DDL等无法使用writeset的操作)
      (writeset->size() != 0 || 
       write_set_ctx->get_has_missing_keys() ||
       is_empty_transaction_in_binlog_cache(thd)) &&
      // 必须是ROW格式binlog
      thd->variables.binlog_format == BINLOG_FORMAT_ROW &&
      // 不能有外键依赖(外键会导致级联操作)
      !write_set_ctx->get_has_related_foreign_keys() &&
      // 没有超过writeset大小限制
      !write_set_ctx->was_write_set_limit_reached();

  bool exceeds_capacity = false;

  if (can_use_writesets) {
    // 【关键】检查是否超过history容量
    // 如果超过，本次计算后会清空history
    exceeds_capacity =
        m_writeset_history.size() + writeset->size() > m_opt_max_history_size;

    // 【关键】遍历writeset，计算冲突
    // last_parent初始化为history的起始点
    int64 last_parent = m_writeset_history_start;
    
    for (auto it = writeset->begin(); it != writeset->end(); ++it) {
      // 在history中查找此hash
      Writeset_history::iterator hst = m_writeset_history.find(*it);
      
      if (hst != m_writeset_history.end()) {
        // 【找到冲突】此行之前被其他事务修改过
        // 冲突事务的序号必须:
        //   1. 大于当前的last_parent (找最大的冲突)
        //   2. 小于当前事务序号 (只看之前的事务)
        if (hst->second > last_parent && hst->second < sequence_number)
          last_parent = hst->second;  // 更新依赖

        // 更新history，记录此hash最新被当前事务修改
        hst->second = sequence_number;
      } else {
        // 【无冲突】新hash，加入history
        // 但如果已超容量，不再添加
        if (!exceeds_capacity)
          m_writeset_history.insert(
              std::pair<uint64, int64>(*it, sequence_number));
      }
    }

    // 【关键】最终commit_parent取WRITESET和COMMIT_ORDER的最小值
    // 即更严格的依赖(更早的可并行点)
    // 但如果有缺失主键的表，不能使用WRITESET优化
    if (!write_set_ctx->get_has_missing_keys()) {
      commit_parent = std::min(last_parent, commit_parent);
    }
  }

  // 【关键】超容量或无法使用writeset时，清空history
  // 清空后，所有事务的commit_parent回退到COMMIT_ORDER结果
  if (exceeds_capacity || !can_use_writesets) {
    m_writeset_history_start = sequence_number;
    m_writeset_history.clear();
  }
}

// ============================================================================
// sql/rpl_trx_tracking.cc:149-178
// COMMIT_ORDER依赖计算核心代码
// ============================================================================
void Commit_order_trx_dependency_tracker::get_dependency(
    THD *thd, bool parallelization_barrier,
    int64 &sequence_number, int64 &commit_parent) {
  
  Transaction_ctx *trn_ctx = thd->get_transaction();

  // 计算相对于当前binlog偏移的sequence_number
  // binlog轮转时offset会更新，确保序号从小开始
  sequence_number =
      trn_ctx->sequence_number - m_max_committed_transaction.get_offset();

  // 计算commit_parent
  if (trn_ctx->last_committed <= m_max_committed_transaction.get_offset())
    // binlog轮转导致的特殊情况
    commit_parent = SEQ_UNINIT;
  else
    // 【关键】commit_parent = max(事务自身记录的last_committed, 阻塞事务序号)
    // m_last_blocking_transaction用于处理某些事务必须阻塞后续事务的情况
    commit_parent =
        std::max(trn_ctx->last_committed, m_last_blocking_transaction) -
        m_max_committed_transaction.get_offset();

  // 【关键】某些SQL不安全，必须设置为阻塞点
  // 后续事务的commit_parent至少要依赖此事务
  if (is_trx_unsafe_for_parallel_slave(thd) || parallelization_barrier)
    m_last_blocking_transaction = trn_ctx->sequence_number;
}

// ============================================================================
// sql/rpl_write_set_handler.cc:676-696
// PKE hash生成核心代码
// ============================================================================
static bool generate_hash_pke(const std::string &pke, THD *thd) {
  DBUG_TRACE;

  // 【关键】使用xxHash64算法计算hash
  // xxHash64是非加密哈希，速度极快，冲突率极低
  uint64 hash = MY_XXH64(pke.c_str(), pke.size(), 0);
  
  // 添加到事务的writeset集合
  if (thd->get_transaction()->get_transaction_write_set_ctx()->add_write_set(
          hash))
    return true;  // 添加失败(超过限制)

  DBUG_PRINT("info", ("pke: %s; hash: %" PRIu64, pke.c_str(), hash));
  return false;
}

// ============================================================================
// sql/rpl_replica_commit_order_manager.cc:337-351
// 从库锁冲突死锁检测核心代码
// ============================================================================
void Commit_order_manager::check_and_report_deadlock(THD *thd_self,
                                                     THD *thd_wait_for) {
  DBUG_TRACE;

  // 获取两个线程对应的Worker
  Slave_worker *self_w = get_thd_worker(thd_self);      // 等待锁的Worker
  Slave_worker *wait_for_w = get_thd_worker(thd_wait_for);  // 持有锁的Worker
  Commit_order_manager *mngr = self_w->get_commit_order_manager();

  // 【关键】检查提交顺序死锁条件:
  // 1. 同一个复制通道
  // 2. self_w(小序号)在等wait_for_w(大序号)的锁
  //    但wait_for_w要等self_w先提交
  //    → 循环等待 → 死锁!
  if (mngr != nullptr && self_w->c_rli == wait_for_w->c_rli &&
      wait_for_w->sequence_number() > self_w->sequence_number()) {
    DBUG_PRINT("info", ("Found replica order commit deadlock"));
    // 报告死锁，让持有锁的Worker回滚
    mngr->report_deadlock(wait_for_w);
  }
}

```
症状：设置了WRITESET但从库并行度不高

## 六、总结与反思

### 6.1 核心要点回顾

1. **三种依赖跟踪策略**：COMMIT_ORDER(锁窗口)、WRITESET(行集合)、WRITESET_SESSION
2. **Writeset原理**：通过PKE hash检测行级冲突
3. **commit_id分配**：sequence_number递增分配，last_committed取min(COMMIT_ORDER, WRITESET)
4. **锁冲突检测**：序号小的等序号大的锁时触发死锁处理
