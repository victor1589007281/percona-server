# MySQL Sidecar Agent 设计文档

> 版本: 1.0
> 日期: 2026-02-05

### 1.2 设计原则

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                            核心设计原则                                      │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  原则 1: 人为操作优先 (Human First)                                         │
│  ────────────────────────────────────                                       │
│  • 检测到人为操作时，Agent 立即暂停自动化动作                               │
│  • 人为操作完成后，等待确认再恢复自动化                                     │
│  • 冲突时以人为决策为准                                                     │
│                                                                             │
│  原则 2: 分级决策 (Tiered Decision Making)                                  │
│  ────────────────────────────────────                                       │
│  • L0 (自动): 监控采集、告警发送、只读分析                                  │
│  • L1 (自动+通知): 低风险修复 (如 kill 慢查询)                              │
│  • L2 (审批后执行): 中风险操作 (如添加索引)                                 │
│  • L3 (仅建议): 高风险操作 (如主从切换、数据变更)                           │
│                                                                             │
│  原则 3: 安全边界 (Safety Boundary)                                         │
│  ────────────────────────────────────                                       │
│  • 永不自动执行 DROP/TRUNCATE/DELETE 等破坏性操作                           │
│  • 自动操作必须可回滚或有补偿措施                                           │
│  • 操作前必须通过安全检查                                                   │
│                                                                             │
│  原则 4: 可观测性 (Observability)                                           │
│  ────────────────────────────────────                                       │
│  • 所有决策过程可追溯                                                       │
│  • 完整的操作审计日志                                                       │
│  • 实时状态可查询                                                           │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 2.2 详细问题与解决方案

#### 2.2.1 性能问题

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         性能问题详细解决方案                                 │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  ╔═══════════════════════════════════════════════════════════════════════╗ │
│  ║ 问题 #1: 慢查询                                                        ║ │
│  ╚═══════════════════════════════════════════════════════════════════════╝ │
│                                                                             │
│  【检测方式】                                                                │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │  -- 1. 实时监控 processlist                                           │  │
│  │  SELECT * FROM information_schema.processlist                         │  │
│  │  WHERE command != 'Sleep'                                             │  │
│  │    AND time > @slow_threshold_seconds;                                │  │
│  │                                                                       │  │
│  │  -- 2. Performance Schema 事件                                        │  │
│  │  SELECT * FROM performance_schema.events_statements_current           │  │
│  │  WHERE timer_wait > @slow_threshold_ns;                               │  │
│  │                                                                       │  │
│  │  -- 3. 慢查询日志 (离线分析)                                          │  │
│  │  SELECT * FROM mysql.slow_log WHERE query_time > @threshold;          │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│  【自动化响应】                                                              │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │                                                                       │  │
│  │  Level 0: 监控 + 记录                                                 │  │
│  │  ─────────────────────                                               │  │
│  │  • 采集慢查询指纹和执行计划                                          │  │
│  │  • 记录到本地存储用于分析                                            │  │
│  │  • 发送告警通知                                                      │  │
│  │                                                                       │  │
│  │  Level 1: 自动 Kill (可配置)                                         │  │
│  │  ─────────────────────                                               │  │
│  │  条件:                                                                │  │
│  │    • 执行时间 > kill_threshold (默认 300秒)                          │  │
│  │    • 非事务性查询 OR 只读事务                                        │  │
│  │    • 非系统用户 (repl, admin 等)                                     │  │
│  │  动作:                                                                │  │
│  │    KILL QUERY {connection_id};                                       │  │
│  │  通知:                                                                │  │
│  │    发送 kill 通知到 DBA                                              │  │
│  │                                                                       │  │
│  │  Level 2: 优化建议 (需审批)                                          │  │
│  │  ─────────────────────                                               │  │
│  │  • 调用 LLM 分析查询并生成优化方案                                   │  │
│  │  • 生成索引建议 (CREATE INDEX)                                       │  │
│  │  • 等待人工审批后执行                                                │  │
│  │                                                                       │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│  ╔═══════════════════════════════════════════════════════════════════════╗ │
│  ║ 问题 #2: 锁等待与死锁                                                  ║ │
│  ╚═══════════════════════════════════════════════════════════════════════╝ │
│                                                                             │
│  【检测方式】                                                                │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │  -- 1. 锁等待监控                                                     │  │
│  │  SELECT * FROM sys.innodb_lock_waits;                                 │  │
│  │                                                                       │  │
│  │  -- 2. 死锁检测 (解析 SHOW ENGINE INNODB STATUS)                      │  │
│  │  SHOW ENGINE INNODB STATUS\G  -- LATEST DETECTED DEADLOCK 部分       │  │
│  │                                                                       │  │
│  │  -- 3. 长事务监控                                                     │  │
│  │  SELECT * FROM information_schema.innodb_trx                          │  │
│  │  WHERE trx_started < NOW() - INTERVAL @threshold SECOND;              │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│  【自动化响应】                                                              │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │                                                                       │  │
│  │  锁等待超时:                                                          │  │
│  │  • 超过阈值 (默认 60秒) → Kill 等待者 (L1)                           │  │
│  │  • 分析锁链，找出阻塞源头                                            │  │
│  │  • 生成锁分析报告                                                    │  │
│  │                                                                       │  │
│  │  死锁发生:                                                            │  │
│  │  • 自动记录死锁信息 (L0)                                             │  │
│  │  • 调用 LLM 分析死锁原因                                             │  │
│  │  • 生成预防建议 (事务顺序、索引优化等)                               │  │
│  │                                                                       │  │
│  │  长事务处理:                                                          │  │
│  │  • 超过阈值 → 告警 + 记录 (L0)                                       │  │
│  │  • 超过危险阈值 → 审批后 Kill (L2)                                   │  │
│  │                                                                       │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│  ╔═══════════════════════════════════════════════════════════════════════╗ │
│  ║ 问题 #3: 连接数过高                                                    ║ │
│  ╚═══════════════════════════════════════════════════════════════════════╝ │
│                                                                             │
│  【检测方式】                                                                │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │  -- 连接数统计                                                        │  │
│  │  SHOW STATUS LIKE 'Threads_connected';                                │  │
│  │  SHOW STATUS LIKE 'Threads_running';                                  │  │
│  │  SHOW STATUS LIKE 'Max_used_connections';                             │  │
│  │                                                                       │  │
│  │  -- 按用户/主机分组                                                   │  │
│  │  SELECT user, host, count(*) FROM information_schema.processlist     │  │
│  │  GROUP BY user, host ORDER BY count(*) DESC;                         │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│  【自动化响应】                                                              │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │                                                                       │  │
│  │  连接数告警 (>80% max_connections):                                   │  │
│  │  • 发送告警 (L0)                                                     │  │
│  │  • 清理空闲连接 (Sleep > 300s) (L1)                                  │  │
│  │                                                                       │  │
│  │  连接数危机 (>95% max_connections):                                   │  │
│  │  • 紧急清理空闲连接 (Sleep > 60s) (L1)                               │  │
│  │  • 建议调整 max_connections (L2)                                     │  │
│  │                                                                       │  │
│  │  连接风暴检测:                                                        │  │
│  │  • 短时间内连接数激增 → 分析来源                                     │  │
│  │  • 可配置自动阻断异常来源 IP (L2)                                    │  │
│  │                                                                       │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│  ╔═══════════════════════════════════════════════════════════════════════╗ │
│  ║ 问题 #4: Buffer Pool 命中率低                                          ║ │
│  ╚═══════════════════════════════════════════════════════════════════════╝ │
│                                                                             │
│  【检测方式】                                                                │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │  SELECT                                                               │  │
│  │    (1 - (Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests))│  │
│  │    * 100 AS hit_ratio;                                                │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│  【自动化响应】                                                              │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │  命中率 < 99%:                                                        │  │
│  │  • 告警 (L0)                                                         │  │
│  │  • 分析是否有大表扫描污染 Buffer Pool                                │  │
│  │  • 建议调整 innodb_buffer_pool_size (L2)                             │  │
│  │                                                                       │  │
│  │  检测到大表扫描:                                                      │  │
│  │  • 识别全表扫描查询                                                  │  │
│  │  • 建议添加索引 (L2)                                                 │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

```
│  │  │                            │                                   │   │  │
│  │  │    有多数派 → 可继续服务  │        无多数派 → 降级只读        │   │  │
│  │  │                            │                                   │   │  │
│  │  └───────────────────────────────────────────────────────────────┘   │  │
│  │                                                                       │  │
│  │  机制 3: Fencing (隔离旧主)                                           │  │
│  │  ─────────────────────────────────                                   │  │
│  │                                                                       │  │
│  │  确保旧主不能继续写入:                                               │  │
│  │  • STONITH: 物理关闭旧主服务器 (Shoot The Other Node In The Head)    │  │
│  │  • 网络隔离: 防火墙规则阻断旧主                                      │  │
│  │  • 存储隔离: 撤销旧主的存储访问权限                                  │  │
│  │  • 软隔离: SET read_only=ON + KILL 所有连接                          │  │
│  │                                                                       │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│  ╔═══════════════════════════════════════════════════════════════════════╗ │
│  ║ 脑裂检测与恢复                                                         ║ │
│  ╚═══════════════════════════════════════════════════════════════════════╝ │
│                                                                             │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │                                                                       │  │
│  │  检测脑裂:                                                            │  │
│  │  • 定期检查仲裁服务中的 leader 信息                                  │  │
│  │  • 发现与本地状态不一致 → 触发脑裂处理                               │  │
│  │  • 发现多个节点声称是 master → 脑裂确认                              │  │
│  │                                                                       │  │
│  │  脑裂处理:                                                            │  │
│  │  ┌────────────────────────────────────────────────────────────────┐  │  │
│  │  │  1. 立即将所有可疑 master 设为 read_only                       │  │  │
│  │  │  2. 停止所有自动故障转移                                       │  │  │
│  │  │  3. 比较各节点 GTID，确定数据最完整的节点                      │  │  │
│  │  │  4. 人工确认后恢复:                                            │  │  │
│  │  │     - 选择正确的 master                                        │  │  │
│  │  │     - 其他节点作为从库重建                                     │  │  │
│  │  │     - 如有数据丢失，通过 binlog 恢复                           │  │  │
│  │  └────────────────────────────────────────────────────────────────┘  │  │
│  │                                                                       │  │
│  │  代码实现:                                                            │  │
│  │  ┌────────────────────────────────────────────────────────────────┐  │  │
│  │  │  func (a *Agent) checkSplitBrain() {                           │  │  │
│  │  │      // 获取仲裁服务中的 leader                                 │  │  │
│  │  │      leader, err := a.arbiter.GetLeader()                      │  │  │
│  │  │      if err != nil {                                           │  │  │
│  │  │          // 无法连接仲裁服务，可能是网络分区                   │  │  │
│  │  │          a.enterSafeMode()                                     │  │  │
│  │  │          return                                                │  │  │
│  │  │      }                                                         │  │  │
│  │  │                                                                │  │  │
│  │  │      // 检查本地状态与全局状态是否一致                         │  │  │
│  │  │      if a.role == Master && leader != a.nodeID {              │  │  │
│  │  │          // 本地认为是主，但仲裁服务不认可                     │  │  │
│  │  │          a.log.Warn("Split brain detected!")                   │  │  │
│  │  │          a.demoteToReadOnly()                                  │  │  │
│  │  │          a.triggerAlert("SPLIT_BRAIN_DETECTED")                │  │  │
│  │  │      }                                                         │  │  │
│  │  │  }                                                             │  │  │
│  │  │                                                                │  │  │
│  │  │  func (a *Agent) enterSafeMode() {                             │  │  │
│  │  │      // 无法连接仲裁服务，进入安全模式                         │  │  │
│  │  │      // 1. 如果是主库，设为只读                                │  │  │
│  │  │      if a.role == Master {                                     │  │  │
│  │  │          a.mysql.Exec("SET GLOBAL read_only = ON")             │  │  │
│  │  │          a.mysql.Exec("SET GLOBAL super_read_only = ON")       │  │  │
│  │  │      }                                                         │  │  │
│  │  │      // 2. 停止自动故障转移                                    │  │  │
│  │  │      a.disableAutoFailover()                                   │  │  │
│  │  │      // 3. 告警                                                │  │  │
│  │  │      a.triggerAlert("SAFE_MODE_ENTERED")                       │  │  │
│  │  │  }                                                             │  │  │
│  │  └────────────────────────────────────────────────────────────────┘  │  │
│  │                                                                       │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 5.2 Hook 执行引擎

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        Hook 执行引擎                                         │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │                                                                       │  │
│  │  type HookExecutor struct {                                           │  │
│  │      config     HookConfig                                            │  │
│  │      httpClient *http.Client                                          │  │
│  │      retrier    *Retrier                                              │  │
│  │      metrics    *HookMetrics                                          │  │
│  │  }                                                                    │  │
│  │                                                                       │  │
│  │  func (h *HookExecutor) Execute(event Event) error {                  │  │
│  │      hooks := h.config.GetHooks(event.Type)                           │  │
│  │                                                                       │  │
│  │      for _, hook := range hooks {                                     │  │
│  │          // 渲染模板                                                  │  │
│  │          body, err := h.renderTemplate(hook.Body, event.Data)         │  │
│  │                                                                       │  │
│  │          // 执行 Hook (带重试)                                        │  │
│  │          err = h.retrier.Do(func() error {                            │  │
│  │              return h.executeHTTP(hook, body)                         │  │
│  │          }, hook.Retry)                                               │  │
│  │                                                                       │  │
│  │          // 记录结果                                                  │  │
│  │          h.metrics.Record(hook.Name, err)                             │  │
│  │                                                                       │  │
│  │          // 根据策略决定是否继续                                      │  │
│  │          if err != nil && hook.Required {                             │  │
│  │              return err  // 必需的 Hook 失败则中止                    │  │
│  │          }                                                            │  │
│  │      }                                                                │  │
│  │      return nil                                                       │  │
│  │  }                                                                    │  │
│  │                                                                       │  │
│  │  Hook 执行策略:                                                       │  │
│  │  • parallel: 并行执行所有 Hook                                       │  │
│  │  • sequential: 顺序执行，前一个成功后执行下一个                      │  │
│  │  • best_effort: 尽力执行，失败不影响主流程                           │  │
│  │  • required: 必须成功，失败则回滚主操作                              │  │
│  │                                                                       │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 8. 安全设计

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           安全设计                                           │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  ╔═══════════════════════════════════════════════════════════════════════╗ │
│  ║ 最小权限原则                                                           ║ │
│  ╚═══════════════════════════════════════════════════════════════════════╝ │
│                                                                             │
│  Agent 使用的 MySQL 用户权限:                                               │
│                                                                             │
│  CREATE USER 'mysql_agent'@'localhost' IDENTIFIED BY 'xxx';                 │
│                                                                             │
│  -- 监控权限 (必需)                                                         │
│  GRANT SELECT ON performance_schema.* TO 'mysql_agent'@'localhost';         │
│  GRANT SELECT ON information_schema.* TO 'mysql_agent'@'localhost';         │
│  GRANT SELECT ON mysql.* TO 'mysql_agent'@'localhost';                      │
│  GRANT PROCESS, REPLICATION CLIENT ON *.* TO 'mysql_agent'@'localhost';     │
│                                                                             │
│  -- 操作权限 (按需)                                                         │
│  GRANT SUPER ON *.* TO 'mysql_agent'@'localhost';  -- Kill, SET GLOBAL     │
│  GRANT RELOAD ON *.* TO 'mysql_agent'@'localhost'; -- FLUSH                │
│  GRANT REPLICATION SLAVE ON *.* TO 'mysql_agent'@'localhost'; -- 复制管理  │
│                                                                             │
│  ╔═══════════════════════════════════════════════════════════════════════╗ │
│  ║ 操作审计                                                               ║ │
│  ╚═══════════════════════════════════════════════════════════════════════╝ │
│                                                                             │
│  所有操作记录到审计日志:                                                    │
│  • 时间戳                                                                   │
│  • 操作类型                                                                 │
│  • 操作者 (Agent/人为)                                                      │
│  • 目标 (SQL/配置/节点)                                                     │
│  • 操作内容                                                                 │
│  • 结果                                                                     │
│  • 回滚信息 (如果有)                                                        │
│                                                                             │
│  ╔═══════════════════════════════════════════════════════════════════════╗ │
│  ║ 敏感信息保护                                                           ║ │
│  ╚═══════════════════════════════════════════════════════════════════════╝ │
│                                                                             │
│  • 密码/密钥从文件读取，不在配置中明文存储                                  │
│  • API 通信使用 TLS                                                         │
│  • 敏感日志脱敏 (密码、数据值等)                                            │
│  • Hook 调用中的敏感数据加密传输                                            │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```
